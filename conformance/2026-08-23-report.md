## Findings

### 1. Cancel Order now allows cancellation within a 24h grace window after capture — contradicting INV-CO-1

- **Surface:** spec
- **Classification:** real drift
- **Slice:** Cancel Order
- **Evidence:**
  - `src/main/kotlin/com/meridiangoods/cancelorder/CancelOrderCommandHandler.kt:44-47` —
    `val CANCELLATION_GRACE: Duration = Duration.ofHours(24)`.
  - `src/main/kotlin/com/meridiangoods/cancelorder/CancelOrderCommandHandler.kt:90-96` — the
    INV-CO-1 check is now `check(capturedAt == null || Duration.between(capturedAt, cancelledAt)
    <= CANCELLATION_GRACE) { ... }`, i.e. cancellation succeeds even after `Payment Captured` as
    long as it's within 24 hours.
  - `src/test/kotlin/com/meridiangoods/cancelorder/CancelOrderAxonFixtureTest.kt:80` — the test
    that used to assert unconditional rejection was renamed to
    `` `INV-CO-1 - given Payment Captured beyond the grace window, when Cancel Order, then rejected as too-late-to-cancel` ``.
  - `src/test/kotlin/com/meridiangoods/cancelorder/CancelOrderAxonFixtureTest.kt:93-104` — a new,
    passing test, `` `cancel within the grace window after capture succeeds (support-requested)` ``,
    proves the new behavior is intentional and shipped, not an accidental regression.
  - Shipped in commit `8f12ed8` ("Cancel decision cleanup; honor the support-requested post-capture
    grace window (#17)"), the tip of this branch.
  - `slices/cancel-order.md`'s **INV-CO-1** text: "an order can be cancelled only BEFORE `Payment
    Captured` exists for it. Once `Payment Captured` has been recorded for an order, a `Cancel
    Order` command for that order is **rejected**" — and its "Rejected — already captured
    (INV-CO-1)" scenario: "Given ... `Payment Captured` has already been recorded for `O1` ...
    Then the command is rejected as too-late-to-cancel and no `Order Cancelled` event is recorded."
    No exception is documented anywhere in the slice doc.
  - `domain-decisions.md`'s "Cancellation" bullet, still current (not superseded/struck through):
    "The load-bearing rule is **INV-CO-1**: an order can be cancelled only *before* `Payment
    Captured` exists for it — cancellation after capture is rejected, not silently allowed or
    auto-refunded."
- **Claim:** both the slice doc and the model-level design-decisions record say capture is an
  absolute bar on cancellation, no exception. The shipped, tested code now allows cancellation up
  to 24 hours after capture. Two independent doc sources agree with each other and disagree with
  the code; this is not a case of one stale doc among several current ones.
- **Proposed red note:** `issue "conformance: INV-CO-1 as coded allows cancellation within a 24h
  grace window after Payment Captured (CancelOrderCommandHandler.CANCELLATION_GRACE) — the doc's
  INV-CO-1 text/scenario and domain-decisions.md's cancellation bullet both still say capture is an
  absolute, exception-free bar. Ratify the grace window into the doc and domain-decisions.md, or
  revert the code to match the ratified rule."` on the `Cancel Order` command element (slice
  "Cancel Order").

### 2. Request Payment's processor never reads Payments To Request — it reacts to Order Placed directly

- **Surface:** spec
- **Classification:** real drift
- **Slice:** Request Payment (and, as the other end of the same claim, Payments To Request)
- **Evidence:**
  - `src/main/kotlin/com/meridiangoods/requestpayment/WhenOrderPlacedThenRequestPayment.kt:42-43` —
    `@EventHandler fun react(event: OrderPlaced, ...)` — the processor's only handler reacts to the
    raw `OrderPlaced` event. Nothing under `com.meridiangoods.requestpayment` imports or queries
    `PaymentsToRequestRepository` / `ListPaymentsToRequestQueryHandler`.
  - `src/main/kotlin/com/meridiangoods/requestpayment/WhenOrderPlacedThenRequestPayment.kt:14-31` —
    the class's own doc comment states this outright: "the slice doc's Trigger & Actor section
    describes this processor as watching the `Payments To Request` read model ... Rather than take
    a ... dependency on a projection that may not exist yet, this automation reacts directly and
    statelessly ... to `Order Placed` itself" and calls this "a technical implementation-mechanism
    choice ... that does deviate from the doc's *described* mechanism."
  - `slices/request-payment.md:20` (Trigger & Actor): "The `Payment Requester` processor watches
    the `Payments To Request` view (built in the slice before, from `Order Placed`) and, for each
    order it finds there, issues the `Request Payment` command."
  - `slices/request-payment.md:53-54`: "once `Payment Requested` lands, `INV-PTR-2` removes the
    order from that queue, so the processor structurally cannot re-select it on a later poll."
  - `slices/request-payment.md:72-74`, the doc's own "Exactly-once under re-poll (INV-RP-1)"
    scenario: "Given `O1` has already produced a `Payment Requested` event (and so is no longer in
    `Payments To Request`), When the processor's next poll runs over the queue, Then O1 is not
    present to select."
  - The `Payments To Request` view (`PaymentsToRequestProjection.kt:23-38`) is real and actively
    maintained (upserted on `OrderPlaced`, removed on `PaymentRequested`) and is separately queried
    by `ListPaymentsToRequestQueryHandler` — so this is not the "legitimately non-materialized
    view" idiom (`reference/conform.md`'s R5 exception); the view exists, works, and is simply never
    consulted by the automation its own doc says consumes it.
- **Claim:** the doc describes a poll/queue-drain mechanism (event → read model → processor reads
  the read model → command) as the reason INV-RP-1 (exactly-once) holds. The actual mechanism is a
  direct, stateless event reaction (event → processor directly → command), with exactly-once
  instead enforced by the command handler's own `orderId`-keyed idempotent-creation state
  (`RequestPaymentCommandHandler.kt:47-49`). The *outcome* (at most one `Payment Requested` per
  order) is preserved, but the *mechanism* the doc and its INV-RP-1 explanation describe is not
  what ships. This is honestly flagged in a code comment, but there is no `divergence "..."`
  annotation on the model's `Payment Requester` element, so it isn't yet a ratified Accepted
  divergence — it's an un-ratified, self-acknowledged deviation.
- **Proposed red note:** `issue "conformance: the Payment Requester processor reacts directly to
  Order Placed (WhenOrderPlacedThenRequestPayment) and never reads the Payments To Request view —
  the doc's Trigger & Actor section and its INV-RP-1 explanation describe a queue-watching/poll
  mechanism that isn't what's built. Outcome parity (exactly-once) is maintained via a different,
  orderId-keyed mechanism in RequestPaymentCommandHandler. Ratify either the doc's described
  mechanism or the code's actual direct-reaction design (e.g. a `divergence` annotation) so this
  stops being an open question."` on the `Payment Requester` processor element (slice
  "Request Payment").

### 3. Record Payment Result: "distinct providerRef" scenario says "rejected"; code executes a silent no-op

- **Surface:** spec
- **Classification:** real drift
- **Slice:** Record Payment Result
- **Evidence:**
  - `slices/record-payment-result.md:82-86`, the "Distinct providerRef is a distinct fact"
    scenario: "Given `Payment Captured` for `P1` already exists ... this case is **rejected** the
    same way an unknown-context duplicate would be."
  - `src/main/kotlin/com/meridiangoods/recordpaymentresult/RecordPaymentResultCommandHandler.kt:54-56` —
    the branch actually taken for this case is `if (state.captured) return emptyList()`, the exact
    same silent-no-op branch INV-RPR-2's ordinary idempotent-retry case uses. There is no
    `providerRef` comparison anywhere in the handler — "already captured" short-circuits
    regardless of which `providerRef` arrives.
  - `src/test/kotlin/com/meridiangoods/recordpaymentresult/RecordPaymentResultCommandHandlerTest.kt:106-118` —
    the test for this exact scenario asserts `.then().success().noEvents()`, not an exception —
    contrast with the true INV-RPR-3 rejection test at `RecordPaymentResultCommandHandlerTest.kt:67-76`,
    which does assert an exception.
- **Claim:** the doc's scenario text promises a *rejection* (an error path, matching the language
  used for INV-RPR-3's genuine rejection); the code and its own test show a *silent success* with
  no event and no exception — behaviorally indistinguishable from an ordinary idempotent retry.
  The observable outcome (no second `Payment Captured`) matches, but "rejected" is not an accurate
  description of what happens.
- **Proposed red note:** `issue "conformance: the 'distinct providerRef' scenario text says this
  case is rejected, but the code (RecordPaymentResultCommandHandler, same branch as INV-RPR-2)
  treats it as a silent no-op indistinguishable from an ordinary idempotent retry — no
  exception/rejection occurs, per its own test. Reword the scenario to describe the actual
  no-op-not-rejection mechanism, or change the code to actually reject a mismatched providerRef,
  whichever the domain intends."` on the `Record Payment Result` command element (slice
  "Record Payment Result").

    ("Implement cancel-order ... (#15)") and `6635462` ("Implement open-orders-cancelled ...

- **Claim:** README.md's own comment calls its generated table "the ONE place slices are

  which is exactly the scoping question this run had to resolve by cross-checking the docs
  directly instead.
- **Proposed red note:** none — this isn't a modeling decision for the `.em` or a slice doc to
  ratify; it's a mechanical staleness fixable by re-running `em slice index meridian-goods.em` to
  regenerate the table from the (correct) doc frontmatter.
